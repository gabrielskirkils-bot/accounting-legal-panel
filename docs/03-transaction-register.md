# 03: The transaction register

The register is the heart of the app. **One business event = one transaction record.** Each record collects *everything* known about the event:
- the document(s);
- the bank line(s);
- the parties;
- the amounts and VAT;
- the accounting;
- the purpose;
- the decisions;
- the links.

Every other view (ledger, VAT, payables, Google Sheet, reports) is derived from it.

## What counts as one transaction

| Event | Built from |
|---|---|
| Purchase on invoice | the received invoice (+ later the payment line or lines) |
| Card or cash purchase | the receipt + the card or cash line |
| Sale | the issued invoice (+ the receipt of payment) |
| Income without an invoice (grant, donation, prize money received) | the bank line (+ agreement or decision) |
| Bank-only event (fees, interest, tax payment, own transfer) | the bank line |
| Loan drawdown or repayment | the bank line + loan agreement |
| Payment to a private person (author fee, prize, honorarium) | contract or decision + bank line |
| Correction or credit note | the new document, linked to the original transaction |
| Non-cash entry (depreciation, accrual, FX, year-end) | generated by the app, with the rule as the "document" |

Supporting documents (order confirmations, delivery notes, reminders, reconciliation acts, debt letters) are **attached** to the transaction they belong to. They never become a transaction of their own.

## Fields of a transaction record

Each field shows where it comes from: **E** = extracted from the document, **B** = bank, **R** = rule (automatic), **D** = Gabriels's decision, **S** = system.

### Identity and status
| Field | Source | Notes |
|---|---|---|
| `txn_no` | S | Per entity per year, gap-free: `BZ-2026-00123`, `GES-2026-00045` |
| `entity` | R→D | Suggested, confirmed by Gabriels |
| `entity_reason`, `entity_confidence` | R | Which rule produced the suggestion (`04` step 8) and its confidence; drives the "confirm all ≥ 95 %" batch |
| `type` | R | purchase, card_purchase, sale, income_other, bank_only, loan, private_payment, correction, non_cash |
| `status` | S | `captured` → `awaiting_decision` → `confirmed` → `posted` → `reconciled` → `locked` |
| `period` | R | Accounting month (economic date); VAT period |
| `created_at`, `confirmed_at`, `confirmed_by`, `posted_at`, `locked_at` | S | |

### Dates
| Field | Source | Notes |
|---|---|---|
| `doc_date` | E | Issue date |
| `supply_date` / `service_from`–`service_to` | E | Decides the economic period and accruals |

### Document
| Field | Source | Notes |
|---|---|---|
| `doc_type`, `doc_no`, `series` | E | |
| `documents[]` | S | All files with role (main, supporting, contract, reminder, act), SHA-256, Drive link |
| `source` | S | email (original sender, message ID), whatsapp (sender), upload, bank |

**Canonical values (the tests and controls use exactly these names):**
- `doc_type`: `invoice`, `advance_invoice`, `credit_note`, `receipt`, `ticket`, `delivery_note`, `order_confirmation`, `contract`, `act` (pieņemšanas-nodošanas akts), `reconciliation_act`, `debt_letter`, `reminder`, `payout_report`, `bank_statement`, `other`. Supporting types (`order_confirmation`, `delivery_note`, `contract`, `reminder`, `reconciliation_act`) are attached to a record and **never counted in totals**.
- `flags`: `amount_mismatch`, `filename_mismatch`, `two_versions`, `wrong_entity_doc`, `MNB`, `internal`, `related`, `cross_entity_payment`, `duplicate_suspect`, `relates_to_prior_year`, `vat_unchecked`, `missing_document`, `income_without_invoice`, `personal_item`, `low_confidence`.

## Lifecycle

1. **captured.** A document or bank line arrives. The record is created with the extracted fields and an `awaiting_decision` card when anything is open.
2. **confirmed.** Gabriels confirms the entity (and answers any decision cards).
3. **posted.** The posting engine writes the journal entry (`06`). The sub-registers update. The document is filed in Drive and the Sheet row is written.
4. **reconciled.** Payment matched and the amounts tie out (the open amount is 0 for settled items).
5. **locked.** The period is closed or the VAT return is filed. After that, changes only go through a correction transaction.

A record can be *posted and unpaid* (a payable) or *paid and missing its document* (a bank line with status `missing`). Both stay visible until they are resolved.

## Google Sheet per entity per year (live mirror)

`Bourzma <YYYY> grāmatvedība` / `Green Echo Studio <YYYY> grāmatvedība` in `<YYYY> Finances/`:

| Tab | Content |
|---|---|
| **Reģistrs** | One row per transaction, **all fields above** (repeating lines and bank lines in compact text), with Drive and app links |
| Banka | One row per bank line with its transaction no. |
| PVN | VAT register per period (purchases, sales) |
| Kreditori / Debitori | Open payables and receivables with ageing |
| Virsgrāmata | General ledger: account balances per month (trial balance) |
| Lēmumi | Open decisions and the decision log |
| Kopsavilkums | Summary: tiles, VAT due, deadlines, control-check status |

- The database is the source of truth. The worker upserts rows by `txn_no` and never duplicates.
- One editable column, "Piezīmes (Gabriels)", is read back hourly. All other columns are protected.
